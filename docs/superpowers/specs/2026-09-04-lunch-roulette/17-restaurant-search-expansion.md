# 17. 식당 수집 확장 (키워드 분할 + 격자)

[← 인덱스](README.md)

장소를 만들 때 카카오 로컬 API로 반경 안 식당을 수집한다. 지금은 질의가 하나(`query=음식점`)라 카카오 규격상 최대 45개만 들어온다.
이 스펙은 키워드 9개와 2×2 격자로 질의를 나눠 여러 번 호출하고 id로 합쳐 45개 벽을 넘긴다. 서버 액션, RPC, 데이터 모델, 화면은 바꾸지 않는다.
결정 기록은 [02-decisions.md](02-decisions.md) D18이다.

## 문제

- 카카오 키워드 검색은 `size` 최대 15, 한 질의의 노출 가능 문서 수(`meta.pageable_count`) 최대 45다. `size`나 페이지 수를 키워도 넘을 수 없다.
- 현재 질의는 `query=음식점`, `category_group_code=FD6`, `x/y/radius`, `sort=distance` 하나뿐이다. 반경이 넓은 번화가에서는 가까운 45곳만 들어오고 나머지는 잘린다.
- 비용은 문제가 아니다. 카카오 로컬 API는 결제 수단 등록이 없고 앱당 일 300,000회 무료다. 한도를 넘으면 과금 대신 429 오류가 오고 앱은 EXTERNAL_API_UNAVAILABLE을 보여 준다.

## 결정 (2026-09-07 브레인스토밍)

| 번호 | 결정 | 이유 |
|---|---|---|
| E1 | 키워드 분할과 격자(rect) 분할을 함께 쓴다 | 키워드 분할만으로는 키워드마다 45개씩 잘리는 한계가 남는다. 격자는 지역별로 45개씩 받아 반경이 클 때 누락이 적다 |
| E2 | 키워드는 대분류 9개: 음식점, 한식, 중식, 일식, 양식, 분식, 아시아음식, 패스트푸드, 술집. 전부 `category_group_code=FD6` | 카카오 카테고리 트리의 2단계 이름과 같아 매칭이 안정적이고 겹침이 적다. "음식점" 기본 질의는 세분류에 안 걸리는 가게(기타, 뷔페, 도시락)를 위해 유지한다 |
| E3 | 카페(CE7)는 수집하지 않는다 | 점심 후보에 디저트 카페가 섞이면 실제 식사 선택이 아니어서 다시 돌리게 된다. 브런치만 고르는 기준이 단단하지 않다 |
| E4 | 장소당 식당은 중심 거리순 200개까지 저장한다 | 상한이 없으면 장소 상세 목록이 수백 행이 되고 퍼스널 맵 마커 클러스터링(B9)이 바로 필요해진다. 200이면 1000m 반경에서도 대부분 잘리지 않는다 |
| E5 | 반경 허용 범위를 100~1000m로 줄인다(기존 100~2000) | 2000m면 3×3 격자가 필요해 호출이 최대 243회, 서버 액션 시간 제한에 걸린다. 점심 도보 반경으로 1000m가 충분하다 |
| E6 | 셀 × 키워드 작업을 동시 5개로 실행한다 | 순차면 최악 108회 왕복으로 수십 초가 걸린다. 카카오의 초당 제한은 공식 수치가 없어 보수적으로 잡고 스파이크에서 확인한다 |
| E7 | 작업 하나라도 실패하면 전체 실패로 본다. 장소를 반쪽 상태로 저장하지 않는다 | 스펙 06 F2 9번과 같다. 부분 성공을 허용하면 사용자는 왜 식당이 적은지 모르고, 재수집 기능이 없어 반쪽 결과가 영구화된다 |
| E8 | 기존 장소 재수집은 이번에 넣지 않는다. 필요하면 장소를 지우고 다시 만든다 | 사라진 식당 처리와 place_restaurants 동기화 규칙이 필요해 B3 장소 수정과 함께 설계한다. 장소를 지워도 식당 경험치는 식당 기준이라 유지되고, 세션은 place_id만 null이 된다 |
| E9 | 화면은 바꾸지 않는다 | 최악 5~6초라 진행 표시가 필요 없다. 결과 문구 "식당 N곳"은 그대로 |

## 수집 알고리즘

입력은 중심 좌표와 반경 R(100~1000m)이다. 출력은 지금과 같은 `FoundRestaurant[]`다.

### 1. 셀 결정

| 반경 | 셀 | 질의 파라미터 |
|---|---|---|
| R ≤ 500m | 1개 | `x`, `y`, `radius=R`(기존 방식) |
| 500m < R ≤ 1000m | 2×2 = 4개 | `rect=x1,y1,x2,y2`. 중심 ±R 정사각형을 넷으로 나눈 사각형. `radius`는 보내지 않는다 |

- 위경도 변환은 위도 1도 ≈ 111,320m, 경도 1도 ≈ 111,320 × cos(위도) m.
- 셀은 서로 겹치지 않고 정사각형을 빈틈없이 덮는다. 정사각형 모서리처럼 반경 밖에 있는 결과는 기존 `distanceMeters` 필터가 걸러 낸다.
- 셀 질의는 `x`, `y`, `sort=distance`를 함께 보낸다. `rect`와 `x/y`의 병용 가능 여부는 공식 문서가 명확하지 않아 스파이크 항목 1에서 확인한다. 안 되면 셀 질의만 `sort=accuracy`로 둔다. 어느 쪽이든 셀당 45개가 넘을 때 어떤 45개가 남는지만 달라진다.

### 2. 작업과 호출

- (셀, 키워드) 한 쌍이 작업 하나다. 작업 안에서는 지금처럼 페이지 1→3을 순차로 요청하고 `meta.is_end`가 true면 멈춘다.
- 작업들은 동시 5개로 실행한다.

| 반경 | 작업 수 (셀 × 키워드) | 최대 호출 | 최대 수신 문서(중복 제거 전) | 예상 시간(호출당 200ms) |
|---|---|---|---|---|
| ≤ 500m | 9 | 27 | 405 | 약 1~2초 |
| 501~1000m | 36 | 108 | 1,620 | 약 4~6초 |

호출 수는 모든 작업이 3페이지를 다 채울 때의 최악값이다. 결과가 적은 키워드는 1페이지에서 `is_end`로 끝나 실제 호출은 이보다 적다.

### 3. 합치기와 상한

1. 모든 작업의 문서를 `kakao:<id>` 키의 Map에 모아 중복을 없앤다. 같은 식당이 "음식점"과 "한식" 양쪽에 걸리는 것이 정상이다.
2. 좌표가 없거나 반경 밖인 문서는 지금처럼 버린다.
3. 중심 거리 오름차순으로 정렬하고 200개까지만 남긴다. 거리가 같으면 id 문자열순으로 고정해 결과를 결정적으로 만든다.

### 4. 실패

- 작업 하나가 `ExternalApiError`를 던지면 아직 시작하지 않은 작업은 시작하지 않고 전체를 던진다. 이미 진행 중인 요청은 끝나도 결과를 쓰지 않는다.
- `createPlace`는 지금처럼 EXTERNAL_API_UNAVAILABLE로 거절하고 아무것도 저장하지 않는다. 오류 코드는 새로 만들지 않는다. [08-errors.md](08-errors.md)
- 결과가 0개면 지금처럼 장소는 저장하고 PLACE_NO_RESTAURANTS를 안내한다.

### 5. 로그

서버 로그에 한 줄씩 남긴다. API 키와 쿼리 문자열은 넣지 않는다.

- 성공: 반경, 셀 수, 호출 수, 중복 제거 전 문서 수, 제거 후 수, 상한 적용 후 수, 소요 ms.
- 실패: 실패한 셀 번호와 키워드, 오류 메시지(`fetchExternalJson`이 만든 것 그대로).

## 코드 구조

`search.ts` 시그니처 `searchRestaurants(center, radiusM)`, `createPlace`, RPC `create_place_with_restaurants`, `FoundRestaurant` 타입은 바꾸지 않는다. Google 어댑터는 건드리지 않는다(B7).

| 파일 | 변경 | 내용 |
|---|---|---|
| `src/places/collect.ts` | 신설 | fetch 없는 순수 함수 셋. `gridCells(center, radiusM)`: 셀 목록(`{ kind: 'radius' }` 하나 또는 `{ kind: 'rect', rect: 'x1,y1,x2,y2' }` 넷). `capByDistance(center, list, max)`: 거리순 정렬 후 자르기. `mapWithConcurrency(items, limit, fn)`: 동시 실행 제한, 하나가 reject하면 새 작업을 시작하지 않고 reject |
| `src/places/kakao.ts` | 수정 | 상수 `KEYWORDS`(9개), `GRID_THRESHOLD_M = 500`, `MAX_RESTAURANTS = 200`, `CONCURRENCY = 5`, `MAX_PAGES = 3`. `searchRestaurants`는 셀 × 키워드 작업을 만들어 `mapWithConcurrency`로 돌리고 Map에 합친 뒤 `capByDistance`. `geocode`와 문서 파싱은 그대로 |
| `src/actions/places.ts` | 수정 | `RADIUS_MAX` 2000 → 1000 |
| `src/app/(app)/places/PlaceForm.tsx` | 수정 | 반경 입력 `max={1000}` |

이미 1000m 넘게 만든 장소는 그대로 둔다. 새 범위는 새로 만들 때만 적용된다.

## 테스트

[11-testing.md](11-testing.md)의 계층 1(순수 함수)과 어댑터 모의 테스트다. 서버 액션 테스트는 `searchRestaurants`를 모의하므로 바뀌지 않는다.

### `tests/places/collect.test.ts` (신설)

- 셀: 500m 이하는 1개, 501m 이상은 4개. 네 셀의 합이 중심 ±R 정사각형을 빈틈없이 덮고 서로 겹치지 않음. 경도 폭이 위도에 따라 cos 보정됨.
- 자르기: 거리순 정렬, 상한 초과 시 먼 것부터 버림, 같은 거리는 id순, 상한 이하면 전부 유지.
- 동시 실행: 동시에 진행 중인 작업이 limit을 넘지 않음, 하나가 reject하면 아직 시작 안 한 작업은 시작되지 않음, 결과 순서가 입력 순서와 같음, 빈 입력이면 빈 배열.

### `tests/places/kakao.test.ts` (개편)

모의 fetch를 URL 파라미터(`query`, `rect`, `page`)로 분기하는 방식으로 바꾼다. 기존의 `pageParam` 순서 단언은 작업별 단언으로 대체한다.

- 500m: 키워드 9개가 전부 질의됨, `radius` 파라미터 사용, `rect` 없음.
- 800m: `rect` 4개 × 9 키워드 = 36 작업, `radius` 없음.
- 작업별로 `is_end`면 다음 페이지를 요청하지 않음, 최대 3페이지.
- 여러 키워드에 같은 id가 나와도 결과에는 한 번만.
- 200개를 넘으면 거리순 200개.
- 작업 하나가 429면 전체 `ExternalApiError`, `status` 보존, 메시지에 키 없음.
- 기존 케이스 유지: 키 헤더와 `no-store`, 반경 밖 제거, 좌표·id 검증, `address_name` 폴백, 형태 오류, JSON 아님, 키 없으면 fetch 전 실패, `geocode` 전부.
